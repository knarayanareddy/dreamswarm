# DreamSwarm review

## Scope and verdict

**Stage:** Rust implementation, not a verified production service. Revision: `5ab911962af21ed14065e861f38fcd310c17b818`. This is a partial static review of the snapshot and four additional pinned source files. Runtime, builds, tests, deployment and security probes were **not run**. Source demonstrates useful controls but also exposes trust-boundary and operational gaps that need verification before autonomous use on valuable workspaces. [Remediation plan](REMEDIATION_PLAN.md).

## Architecture and product boundary

The [README:17-21](https://github.com/knarayanareddy/dreamswarm/blob/5ab911962af21ed14065e861f38fcd310c17b818/README.md#L17-L21) describes a persistent autonomous engineering daemon. The observed container entry point is `dreamswarm`, defaulting to `--help` ([Dockerfile:51-55](https://github.com/knarayanareddy/dreamswarm/blob/5ab911962af21ed14065e861f38fcd310c17b818/Dockerfile#L51-L55)). The sampled [API server](https://github.com/knarayanareddy/dreamswarm/blob/5ab911962af21ed14065e861f38fcd310c17b818/src/api/server.rs#L75-L120) constructs a local HTTP router including control, configuration and swarm launch. The sampled [agent loop](https://github.com/knarayanareddy/dreamswarm/blob/5ab911962af21ed14065e861f38fcd310c17b818/src/runtime/agent_loop.rs#L130-L230) asks the permission gate before calling a tool. These are observed functions, not proof of every production entry point or executor wiring. The manifest includes Axum, HTTP, SQLite and S3 dependencies ([Cargo.toml:19-27](https://github.com/knarayanareddy/dreamswarm/blob/5ab911962af21ed14065e861f38fcd310c17b818/Cargo.toml#L19-L27)); provider connectivity and storage use were not traced. TUI, static dashboard and examples are distinct surfaces; no nested application behavior was established.

## Findings ledger

- **DS-1 — Medium, confirmed static; high confidence.** [CI:43-48](https://github.com/knarayanareddy/dreamswarm/blob/5ab911962af21ed14065e861f38fcd310c17b818/.github/workflows/ci.yml#L43-L48) runs `crate-ci/typos@master`. The branch can change third-party CI code without a reviewed repository change. Pin a verified full commit SHA and maintain it through reviewed updates.
- **DS-2 — Medium, confirmed static; high confidence.** [Docker workflow:32-39](https://github.com/knarayanareddy/dreamswarm/blob/5ab911962af21ed14065e861f38fcd310c17b818/.github/workflows/docker.yml#L32-L39) pushes `:latest` for non-PR runs, including tag pushes. This moving reference complicates provenance and rollback; publish immutable revision/version references and deploy by digest.
- **DS-3 — High, unverified risk; medium confidence in the observed code, low confidence in end-to-end exposure.** The [bash tool](https://github.com/knarayanareddy/dreamswarm/blob/5ab911962af21ed14065e861f38fcd310c17b818/src/tools/bash_tool.rs#L14-L117) checks regex patterns then invokes `bash -c`; the [agent loop](https://github.com/knarayanareddy/dreamswarm/blob/5ab911962af21ed14065e861f38fcd310c17b818/src/runtime/agent_loop.rs#L140-L230) separately applies `permission_gate.check`. Regex filtering is not proof of confinement. [DreamSandbox](https://github.com/knarayanareddy/dreamswarm/blob/5ab911962af21ed14065e861f38fcd310c17b818/src/dream/sandbox.rs#L1-L100) implements an operation allowlist, budget check and sensitive-name substring filter; its validation and actual callers were not traced. Neither this separate sandbox nor the sampled Bash code establishes the isolation of all executors. Map and test each reachable execution path before granting access to real workspaces; do not conclude other defenses are absent.
- **DS-4 — Medium, unverified risk; medium confidence in dependency inventory.** SQLite and S3 appear in [Cargo.toml:23-27](https://github.com/knarayanareddy/dreamswarm/blob/5ab911962af21ed14065e861f38fcd310c17b818/Cargo.toml#L23-L27). Actual persistence, secret retention, access controls, backup and restore are unverified. Trace stored data and establish retention and recovery requirements before deployment.
- **DS-5 — Informational, historical CI; high confidence in snapshot record.** [CI](https://github.com/knarayanareddy/dreamswarm/actions/runs/41672052020), [Docker](https://github.com/knarayanareddy/dreamswarm/actions/runs/41672052047) and [Documentation](https://github.com/knarayanareddy/dreamswarm/actions/runs/41672051804) report success at the pinned SHA. We did not reproduce them or inspect individual job logs; they do not establish runtime security.
- **DS-6 — High, confirmed static; high confidence for the function, impact conditional on local-user/log access.** [API server](https://github.com/knarayanareddy/dreamswarm/blob/5ab911962af21ed14065e861f38fcd310c17b818/src/api/server.rs#L75-L192) logs `Oracle API bearer token: {}` and substitutes the shared token into the dashboard before bearer authorization. It binds `127.0.0.1`, validates Host and optional Origin, and requires bearer authorization elsewhere: these are real controls. A local client must use an accepted Host and either omit Origin or supply a matching Origin to reach this bootstrap; such a client can obtain the shared token, and log readers may obtain it too. The telemetry query token is the same bearer despite the stream-scoping comment. Define the local-user trust model, remove token logging and use an authenticated bootstrap and genuinely scoped streaming credentials if isolation is required.
- **DS-7 — Medium, confirmed static; high confidence for these handlers only.** [API control handlers](https://github.com/knarayanareddy/dreamswarm/blob/5ab911962af21ed14065e861f38fcd310c17b818/src/api/server.rs#L240-L310) log `control_signal` then return `Manual Deep Dream initiated` or `War Room stress cycle broadcasted`; the handlers do not themselves invoke a dream or war-room operation. An unseen telemetry consumer could act on events, so end-to-end initiation remains unverified. Trace the consumer and report accepted/confirmed/failure states rather than asserting completed work.

## Five-discipline assessment

- **Correctness/code review:** DS-7 can mislead operators if no event consumer performs the action. The loop has an iteration limit; the `CostLimit` stop reason exists, but its complete cost enforcement and caller paths were not established ([agent loop](https://github.com/knarayanareddy/dreamswarm/blob/5ab911962af21ed14065e861f38fcd310c17b818/src/runtime/agent_loop.rs#L1-L100)). Provider errors, cancellation and concurrent writes remain unverified.
- **Automation/testing:** [CI:20-71](https://github.com/knarayanareddy/dreamswarm/blob/5ab911962af21ed14065e861f38fcd310c17b818/.github/workflows/ci.yml#L20-L71) defines formatting, Clippy, OS compilation and tests; [verification:13-17](https://github.com/knarayanareddy/dreamswarm/blob/5ab911962af21ed14065e861f38fcd310c17b818/.github/workflows/verification.yml#L13-L17) names focused integration tests. Test assertions and required branch protection were not inspected.
- **DevOps/operations:** the [Dockerfile:37-43](https://github.com/knarayanareddy/dreamswarm/blob/5ab911962af21ed14065e861f38fcd310c17b818/Dockerfile#L37-L43) sets a non-root user. Release signing, daemon restart, persistent-volume recovery and digest deployment are not verified; DS-2 impedes reproducibility.
- **OWASP/security:** DS-3 and DS-6 concern authorization, command/prompt injection and credential handling. Loopback and permission checks are evidence of defenses, not proof of complete isolation. `Cargo.lock` exists and [dependency-audit:19-24](https://github.com/knarayanareddy/dreamswarm/blob/5ab911962af21ed14065e861f38fcd310c17b818/.github/workflows/dependency-audit.yml#L19-L24) defines audit checks; their current results and dependency integrity were not assessed. Encryption, redaction, retention and per-user authorization are unknown; no secret values were collected.
- **UI/UX/accessibility:** the dashboard is served by the API and TUI files exist; keyboard, screen-reader and error-state behavior were not examined. DS-7 affects status honesty. Test terminal and browser surfaces separately; do not infer accessibility from file presence.

## Production blockers and owner questions

Before production, establish the permitted workspace and local-user threat model, verify tool isolation and authorization for every executor, correct or explicitly accept DS-6/DS-7, and observe recovery and release rollback. Owner must decide API exposure, provider credentials and approved endpoints, registry/signing, retention, restore objectives and supported clients. No certification or production-readiness claim is made.
